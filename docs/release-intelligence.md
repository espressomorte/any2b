# Release Intelligence: специфікація модуля

Статус: Kotlin/JVM-парсер підключено до пошуку, RSS-каталогу та сумісного API метаданих у гілці `experiment/release-intelligence`.

Поточна реалізація: `ReleaseModels.kt`, `KotlinReleaseParser.kt`, `TechnicalRules.kt` і регресійні тести в `release-intelligence/src`. Підтримуються альтернативні назви зі spaced `/` та `|`, роки в дужках, явні сезони/серії, цілі локалізовані епізодні блоки з відомим/невідомим total, відео/аудіотеги, HDR/DV, Theatrical Cut і обмежений словник груп. Мови аудіо й субтитрів розділені; префікси 2x/3x зберігаються як кількість доріжок. Докази посилаються на незмінений UTF-16 рядок. Для лічильника без явного початку припущення позначається ASSUMED_EPISODE_START. Поточна rulesVersion — 3.

Джерела та межі адаптації технічних правил: [RULES.md](../release-intelligence/RULES.md). Це вибіркова Kotlin-адаптація перевіреної поведінки, а не повний порт усього PTT/RTN. Правило визначення мови за кирилицею не використовується.

[Початковий аудит Toloka](release-parser-toloka-random-20.md) дав 4/20 повних розборів; [після адаптації](release-parser-toloka-random-20-upgraded.md) — 20/20 на тих самих заголовках і незмінених ручних очікуваннях. `TolokaRandomSampleTest` тепер є строгим регресійним тестом: очікуваних помилок немає. Вибірка 20 назв AniTube також проходить. Це результат на навчальній регресійній вибірці, а не оцінка точності на всьому трекері.

Інтеграція: `core` залежить від нового модуля; Android TV отримує його транзитивно через `core`. `TolokaReleaseMetadataParser` є адаптером до нового parser, його старий regex-рушій видалено. Збережено API для UI та відтворення, а також перетворення абсолютних серій на сезони TMDB. `TolokaTitleAliases`, `TolokaHitFilter`, `TolokaTmdbRanker` і `TolokaRssTmdbCatalog` використовують спільні назви, роки й сезони. Числа в назвах не шукаються окремими regex року у фільтрах.

RSS використовує новий автоматичний кеш `toloka-rss-tmdb-v3.json`. Ключ включає ID Toloka, SHA-256 заголовка, тип каталогу та версії parser/rules; релізи різних сезонів не об'єднуються за першою назвою. Старий кеш не видаляється; ручні підтвердження залишаються в окремих сховищах. Наявні RSS-прив'язки можуть показуватися до першого оновлення; явний no-match нового parser має пріоритет над старою RSS-прив'язкою. Після першого оновлення каталог повторно шукає автоматичні відповідності.

Збережено сезонні формати `2nd Season`, `2 сезон`, позначені серії й діапазони файлів. Окремий filename `Episode 12` не вважається доказом абсолютної нумерації для перетворення на сезони. Додано альтернативні назви в дужках з іншою писемністю. Для сумісності з Android 21 розпізнавання писемності не використовує Character.UnicodeScript.

Подальша робота: ширший незалежний корпус, загальна контекстна класифікація суфікса для заголовків без року, HTML-декодування з картою позицій, тип озвучення та виділення matcher/ranker в нейтральний модуль. Наявні ранжувальники залишаються в core і споживають результати нового parser. Решта документа описує цільовий контракт; це не перелік уже реалізованих можливостей.

## Задача

Перетворювати заголовок релізу на структуровані факти та окремі назви для пошуку, а потім пояснювано оцінювати відповідність релізу конкретному фільму або сезону. Однаковий вхід і версія правил повинні давати однаковий результат у CLI та Android TV.

Цільова структура — окремий Gradle-модуль `:release-intelligence`, пакет `ua.any2b.release`, Kotlin/JVM із сумісним з Android JVM target 17. Залежності `tv-player → core → release-intelligence`; зворотних залежностей немає.

Модуль не виконує HTTP-запити, не читає RSS/HTML, не зберігає облікові дані, не викликає LLM і не керує UI. Мережевий пошук TMDB/AniList, кеш та ручні підтвердження залишаються в адаптерах застосунку. Порядок карток каталогу за свіжістю та рейтингом також залишається окремою задачею.

## Що вже є в any2b

| Компонент | Поточна відповідальність | План |
| --- | --- | --- |
| `core/.../toloka/TolokaReleaseMetadata.kt` | Теги, сезони, серії, qualityScore, перетворення абсолютних серій на сезони TMDB | Перенести виділення фактів; відокремити оцінку якості й прив'язку до каталогу |
| `core/.../toloka/TolokaTitleAliases.kt` | Поділ назв за мовними варіантами | Замінити адаптером до titleCandidates |
| `core/.../toloka/TolokaTmdbRanker.kt` | Відеофільтр, назви, роки, сезони, fuzzy та якість в одній оцінці | Передавати нейтральний MatchTarget, повертати рішення з причинами |
| `core/.../toloka/TolokaHitFilter.kt` | Окремі regex року/сезону та фільтрація для AniList | Використовувати ті самі факти й правила відповідності |
| `tv-player/.../data/TolokaRssTmdbCatalog.kt` | Власні names(), YEAR, видалення дужок, fuzzy | Використовувати спільні кандидати та роки |
| `core/.../matcher/SeriesTitleSearch.kt` | Варіанти пошукових запитів із сезоном | Узгодити розпізнавання сезону; залишити специфічне формування запитів адаптеру |
| `tv-player/.../data/TolokaRssRanker.kt` | Сортування карток каталогу | Залишити без перенесення |

Зараз парсер видаляє знайдені теги в усьому заголовку, а RSS бере префікс до першого року й видаляє всі дужки. Через це альтернативні назви, числові назви й технічні слова всередині назви потребують окремих регресійних прикладів. `TolokaTitleAliases` уже розділяє білінгвальні назви: цю можливість слід зберегти, а не будувати повторно паралельним шляхом.

## Контракт

Публічні операції (назви попередні):

```kotlin
interface ReleaseParser {
    fun parse(input: ReleaseInput): ParsedRelease
}
interface ReleaseMatcher {
    fun evaluate(release: ParsedRelease, target: MatchTarget): MatchDecision
}
interface ReleaseRanker {
    fun rank(candidates: List<EvaluatedRelease>, profile: RankingProfile): List<EvaluatedRelease>
}
```

| Модель | Обов'язковий зміст |
| --- | --- |
| ReleaseInput | rawTitle, sourceHint: TOLOKA / ANITUBE / GENERIC; опціональні структуровані відомості джерела |
| ParsedRelease | rawTitle, parserVersion, rulesVersion, titleCandidates, years, episodeCoverage, video, audio, subtitles, releaseGroups, contentKind, evidence, warnings |
| TitleCandidate | Текст для показу, нормалізований ключ для порівняння, діапазон у вихідному рядку, scriptHint, ознака неоднозначності |
| Evidence | ruleId, діапазон UTF-16 у rawTitle, виділене значення; результат можна перевірити за оригіналом |
| EpisodeCoverage | Окремі типи SeasonEpisodes, AbsoluteEpisodes, SeasonPack, Unknown; початок/кінець/total опціональні, без вигаданих значень |
| MatchTarget | Підтверджені назви/aliases, тип медіа, рік або роки сезону, очікуваний сезон, кількість серій, опціональна карта сезонів |
| MatchDecision | ACCEPT / REVIEW / REJECT, reasonCodes, оцінка відповідності окремо від якості |
| RankingProfile | Вподобання аудіо/субтитрів, обмеження пристрою, пріоритети джерела й якості; версія профілю |

`null`/Unknown означає «невідомо», а не відсутність або невідповідність. Кирилиця не доводить українську мову, латинка не доводить англійську чи romaji. Парсер повертає підказку писемності; мовну роль можна уточнити лише з даних джерела/каталогу.

## Послідовність та правила

1. Зберегти rawTitle. Декодувати HTML сутності й нормалізувати Unicode у робочому представленні з відображенням позицій на оригінал. Не транслітерувати й не видаляти діакритику з тексту для показу.
2. Розпізнати захищені складені токени: H.264, H.265, 5.1, 7.1, WEB-DL, 10-bit, S01E01-12. Крапки та підкреслення сценічного запису нормалізувати лише після виділення фактів. `Mr. Robot` має зберігатися як пошукова назва.
3. Класифікувати вміст дужок та суфікси справа наліво. Відомий технічний блок, діапазон серій і група озвучення стають фактами з evidence. Невідомі дужки зберігати; `[Oshi no Ko]` та `Movie (Director's Cut)` не можна сліпо стирати.
4. Шукати сезони й серії за пріоритетом: явний SxxExx, явний сезон/пакет сезонів, локалізований лічильник, контекстний діапазон. Покривати `з`, `із`, `of`, дефіс і тире. Для `01-28 з 28` початок саме 1; для `13-28 з 28` — 13. Валідація: start ≤ end ≤ total, якщо total відомий. Невалідне значення породжує warning і не стає достовірним покриттям.
5. `01-24` без контексту не доводить діапазон серій. `12 з 24` означає випущену кількість; трактування 1–12 дозволяється лише правилом джерела, і це припущення позначається. `S00` та specials не переводити у звичайні сезони.
6. Рік у `(2023-2024)` — інтервал, не колекція з двох фільмів. Зберігати роль року: releaseYear / airingRange / uncertain. `1917`, `1984`, `2001: A Space Odyssey`, `Blade Runner 2049` не обрізати за першим чотиризначним числом. Без контексту число залишається частиною назви або неоднозначним фактом.
7. Відео, джерело, кодек, бітність, HDR, аудіокодек і канали — окремі поля. Не ототожнювати AC-3 з E-AC-3, DTS з DTS-HD, DVDRip з HDTV. HEVC і MKV самі по собі не доводять кращу якість або сумісність.
8. Аудіо та субтитри розбирати окремими контекстами: `Ukr/Jap | Sub Ukr` → аудіо uk/ja, субтитри uk. `Sub Ukr` не доводить українське аудіо. Dub/MVO та назва студії — окремі факти; невідомі мови/студії не домислювати.
9. Межу назви визначати контекстом технічного суфікса. Не відкушувати все після першого слова, схожого на тег: `The WEB`, `Dub`, `Sub` можуть бути частиною назви. Групи можуть бути префіксами, зокрема `[SubsPlease] Title ...`.
10. Розділяти `/` та `|` на альтернативні назви тільки всередині області назви після класифікації технічних блоків. `Ukr/Jap` не породжує назви; `Fate/stay night` не розрізається за кожним `/`. Назви в дужках можуть бути додатковими кандидатами.
11. Порожній або пошкоджений заголовок повертає частковий результат із warnings. Обмежити вхід до 4096 UTF-16 одиниць: довший вхід зберегти, припинити повний розбір із INPUT_TOO_LONG і не дозволяти автоматичний матч. Regex мають обмежені класи та проходи, без довільних вкладених `.*`.

Це набір версійованих правил із прикладами. «50–70 рядків regex» не є критерієм успіху: важливі збереження назв, точність фактів і відсутність регресій.

## Відповідність, фільтрація та порядок

Спочатку визначаємо відповідність тайтлу, потім ранжуємо придатні релізи. Сумарна якість та seeders не повинні компенсувати неправильний сезон або назву.

- ACCEPT: переконлива відповідність хоча б одного кандидата назви, немає достовірного конфлікту типу/сезону/року. Самого збігу якості або року недостатньо.
- REVIEW: неоднозначна назва, непевний рік, суперечливі дані, непідтверджена нумерація серій. Відсутній рік сам по собі не є причиною REJECT.
- REJECT: доведений інший сезон/тайтл або підтверджений невідеоконтент. Слово FLAC як аудіодоріжка відеорелізу не робить реліз музичним.
- Абсолютні серії переводяться в сезони лише за достатньої карти епізодів; Unknown не означає «не той сезон». Парсер не залежить від TmdbSeason: адаптер передає нейтральну карту сезонів.
- Ручне відхилення має пріоритет. Підтвердження прив'язується до ID джерела/релізу й цільового каталогу; перенесення на схожі назви — лише підказка для REVIEW. Стару поведінку learnedTitles змінювати окремо з міграційними тестами.
- Для прийнятих релізів: відповідність → сумісність пристрою → мовні вподобання → якість/джерело → доступність → стабільний ID. Жорсткі вимоги профілю застосовувати перед сортуванням; невідомі можливості пристрою не вважати несумісністю.
- Причини: TITLE_MATCH, TITLE_AMBIGUOUS, YEAR_CONFLICT, SEASON_CONFLICT, EPISODE_OVERFLOW, NON_VIDEO, UNKNOWN_COVERAGE, MANUAL_CONFIRMATION. Числові пороги калібрувати на корпусі; не називати score імовірністю.

## Приклад очікуваного результату

```text
Проводжальниця Фрірен / Sousou no Frieren [01-28 з 28] (2023-2024) WEB-DL 1080p Ukr/Jap | Sub Ukr [Amanogawa & FanVoxUA]

titleCandidates = [Проводжальниця Фрірен, Sousou no Frieren]
years = airingRange(2023, 2024)
episodeCoverage = AbsoluteEpisodes(start=1, end=28, total=28)
season = unknown
video = source:WEB-DL, resolution:1080p, codec:unknown
audio.languages = [uk, ja]
subtitles.languages = [uk]
releaseGroups = [Amanogawa, FanVoxUA]
```

Обидва кандидати доступні для пошуку; їхній порядок залежить від каталогу. Успішний парсинг не гарантує, що TMDB/AniList знайде тайтл. LLM не потрібна для цього розбору; невирішений матч залишається REVIEW.

## Готові бібліотеки та словники

Першу реалізацію робимо Kotlin: вона використовує наявний код, працює офлайн на TV та не потребує Python runtime або JNI. Межа ReleaseParser дозволяє пізніше порівняти інший рушій на тому самому корпусі.

- [PTT](https://github.com/dreulavelle/PTT) описує себе як Python-порт parse-torrent-title.
- [RTN](https://github.com/dreulavelle/rank-torrent-name) — окремий проєкт парсингу й ранжування; це не назва Rust-рушія.
- [torrent-parse-rank](https://github.com/g0ldyy/torrent-parse-rank) — окремий Rust-порт із Python API. Рішення про Android-інтеграцію потребує вимірювань і перевірки пакування ABI. Заявлену швидкість не переносимо на наш RSS-кеш без власного benchmark.
- [TRaSH Custom Formats](https://trash-guides.info/Sonarr/sonarr-collection-of-custom-formats/) та [Anime Profiles](https://trash-guides.info/Sonarr/sonarr-setup-quality-profiles-anime/) використовуємо як джерело прикладів і вибраних правил. Оцінки є вподобаннями профілю. Hardsub, dual audio та 10-bit не отримують універсального «погано/добре».

Для запозичених правил записувати URL, ревізію, ліцензію/атрибуцію та власні тести. Не завантажувати живі regex під час виконання. Сумісність regex із JVM перевіряти явно.

## Етапи впровадження

1. Зібрати версійований корпус реальних заголовків Toloka/AniTube та сценічних назв із вручну перевіреними очікуваннями. Зафіксувати поточні результати наявних тестів і окремо відомі помилки.
2. Створити модуль, нейтральні моделі й parser. Перенести перевірені правила, додати evidence та регресії. Залишити старі API через адаптери, не міняти ранжування в цьому кроці.
3. Підключити titleCandidates/years до RSS, aliases та обох фільтрів. Спочатку порівняти старий і новий результати на корпусі без подвійних мережевих запитів. Змінити версію похідного кешу; зберегти ручні мапінги окремо. Новий ключ має враховувати джерело, ID, сезон/покриття та версії, щоб не зливати сезони за однією назвою.
4. Виділити matcher і ranker, калібрувати рішення та профіль. Замінювати старі правила лише після перевірки розбіжностей; забезпечити повернення до попереднього адаптера на час міграції.
5. Порівнювати PTT/Rust лише якщо вимірювання виявлять недолік Kotlin-реалізації за точністю або часом.

## Критерії приймання

- Усі перевірені випадки поточних Toloka-тестів зберігаються або мають явно погоджену корекцію очікувань.
- Приклад Frieren розбирається саме як наведено; додатково покриті `13-28 із 28`, S01E01-12, сезонні пакети, specials, невідомі дужки, Fate/stay night, числові назви, Mr. Robot, H.264, 5.1 та окремий контекст Sub Ukr.
- Неповні, конфліктні й переставлені технічні блоки не спричиняють exception або довільного підтвердження відповідності.
- Пара «не той сезон у 2160p» та «правильний сезон у 720p» доводить, що якість не перекриває конфлікт сезону.
- Корпус оцінюється окремо за точністю назв, років, покриття й мов, а matcher — за хибними автоматичними прив'язками та часткою REVIEW. До увімкнення автоматичних прив'язок: жодної відомої хибної ACCEPT на перевіреному корпусі; це не гарантія для невідомих даних.
- Benchmark публікує розмір корпусу, пристрій/JVM, warm-up, p50/p95, час усього кешу й алокації. Бюджет затверджується після baseline на цільовому TV; «мілісекунди без витрат CPU» не є вимогою.
- У модулі немає Android, HTTP, TMDB/AniList моделей і дискового кешу. Результати детерміновані, причини рішень доступні для діагностики.
